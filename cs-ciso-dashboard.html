01 — The Brief

Siloed vulnerability reporting. No single picture of risk.

Security organizations managing modern infrastructure face a fragmented vulnerability reporting landscape. Dashboards for host vulnerabilities, configuration risks, container security gaps, and application flaws each lived in separate silos — different severity taxonomies, different reporting cadences, different definitions of “critical.”

For vulnerability managers reporting to CISO and CSO leadership, this meant manually reconciling data from across the platform just to answer a single question: what does our attack surface look like right now?

The goal: design a Unified Vulnerability Management Dashboard — a single place to understand full security posture across all asset types, organized by business unit, with the ability to set and track remediation targets.

Problem signals from discovery research
Siloed views
Vulnerability data was split across separate dashboards by asset type — host, container, configuration, and application. Each used a different taxonomy and had no way to roll up into a unified posture view.
∼18 min
Average time to answer “what is our current attack landscape?” A question that should take under 60 seconds required manual reconciliation across multiple reporting views.
No targets
Teams could monitor current vulnerability state, but had no native way to set remediation goals, track progress against them, or surface that progress for leadership.
02 — Discovery

The data existed. The context did not.

Security platforms don’t suffer from data poverty. They suffer from information architecture poverty. Every scanner logs accurately within its own domain — but logs are not decisions. Discovery work with security teams surfaced a problem more organizational than technical.

When vulnerability managers needed to report upward, they were reconciling data across separate reporting views, each with its own definition of severity and its own asset taxonomy. The fragmentation was a strategic blind spot: attack paths don’t respect dashboard boundaries.

A misconfiguration in a container could expose a host vulnerability, which could be exploited via an application weakness — and no existing view showed that chain. Security teams had built elaborate workarounds: spreadsheets, Slack threads, weekly email digests.

The core insight: vulnerability managers weren’t asking “what happened?” They were asking “which team is most exposed, and how fast are they fixing it?” No single view answered that.

01
Stakeholder Interviews
Structured 60-min sessions with vulnerability managers and CISO/CSO stakeholders. Mapped decision-making workflows, reporting chains, and the exact questions leadership asked that existing views couldn’t answer fast enough.
02
Workflow Shadowing
Observed vulnerability managers conducting their weekly posture reviews end-to-end. Mapped every dashboard-switch, manual reconciliation step, and workaround — surfacing the real workflow, not the intended one.
03
Jobs-to-be-Done Analysis
Synthesized interview transcripts into core JTBD statements. Identified which jobs the existing reporting landscape supported, which it partially covered, and which it failed entirely — particularly target-setting and BU-level roll-ups.
04
Competitive Audit
Analyzed competing vulnerability management platforms against identified user jobs. Found a consistent gap: no platform organized vulnerability data by business unit or offered in-product target-setting as a first-class feature.
03 — What We Learned

Fragmented data, fragmented decisions — one unified need.

Discovery collapsed into four sharp insights — each one a structural failure of how vulnerability data was organized, not a failure of the data itself.

01
Business units — not asset types — are the unit of accountability
Vulnerability managers don’t think in terms of “host vs. container vs. application.” They think in terms of business ownership: which team owns this service, which BU is responsible for remediation. Organizing data by asset type was the wrong axis for actual decision-making and leadership reporting.
02
Severity is a local dialect, not a universal language
“Critical” means different things depending on which scanner produces it — the exploitability, blast radius, and remediation urgency vary significantly by vulnerability domain. Without normalization, rolling up severity across domains produces numbers nobody trusts — or that actively mislead leadership.
03
Role-based access must follow organizational structure
CISOs need the full picture. BU security leads need their domain only. External partners need scoped, time-limited views. Without access following the org hierarchy, teams see either too much (cognitive overload) or the wrong things (broken accountability).
04
Target-setting is the missing workflow
Vulnerability management without goals is just monitoring. Security teams needed a way to set remediation targets, track progress against them, and communicate that progress to leadership — a workflow that no reporting view in the platform supported. Without it, every progress conversation required manual report-building.
“I spend two hours every Monday building a report. The data is all there — I just have to find it, reconcile it, and then explain why the numbers don’t match. It shouldn’t be this hard.”

06 — The Design

Unified by business unit. Navigable by risk.

The dashboard resolves around four design principles: a normalized severity model; BU-level organization as the primary axis; target-setting as a first-class workflow; and role-based access that follows the org hierarchy — not scanner or asset ownership.

Executive View
Security posture overview. Goals, health of business-critical entities, scan coverage, MTTR, and vulnerability distribution — all normalized across vulnerability domains. Designed for a 5-minute posture read at the executive level.
Operations View
Operations risk summary. A multi-column layout covering Risk Exposure, Compliance, Security Incidents, Vulnerabilities, and Audits — designed for the vulnerability manager’s daily workflow.
Target Setting
Remediation targets. Active targets appear inline with the live metrics they track — not buried in a settings module. Progress is visible in the same view where vulnerabilities are monitored.
Detail View
Business criticality detail. Drill-down from the posture overview to an entity-level view — surfacing vulnerability impact, asset criticality, and remediation status for a specific business unit or service.
Feature Spotlight

Target-setting: the workflow nobody had but everyone needed.

Every team we spoke with was monitoring vulnerabilities. None of them had a formal process for setting remediation goals and tracking progress against them. No existing view in the platform had a concept of targets — just current state.

We designed target-setting as a native, inline feature: visible in the main dashboard, not buried in settings. A vulnerability manager can define a target — specifying scope, the metric it tracks, the goal value, and the review timeline — and that target appears alongside the live metric it tracks. Progress is immediate and transparent.

This single feature changed how leadership interacted with the dashboard. CISOs moved from passive consumers to active goal-setters. Accountability became visible to everyone, from analyst to executive.

Setting a Target

The Create Target form captures four inputs: visibility scope, the metric being tracked, the goal value, and the review timeline. Progressive disclosure keeps it lightweight while supporting complex remediation configurations.

07 — Key Design Decisions

Where the design got hard.

Three decisions shaped the architecture of the dashboard more than any other — each requiring alignment across design, engineering, and security operations.

Decision 01
Should each domain’s native severity labels be preserved, or normalized to a unified scale?
The tension
Security engineers trusted their domain’s native labels. Leadership wanted a single number to compare across domains. Preserving native labels kept analyst trust; normalizing them enabled meaningful roll-ups. Both were right.
What we chose
A weighted cross-domain severity model mapping each domain’s taxonomy to a unified 1–100 risk score. Summary views show one normalized number; drill-down views preserve native labels alongside the normalized score. Analysts keep their context. Leadership gets comparability.
Decision 02
Should the primary axis be asset type (host, container, app) or business unit?
The tension
Asset type is how scanners generate data. Business unit is how organizations assign accountability. These are fundamentally different hierarchies — choosing the wrong default makes the dashboard useful to engineers but useless to the people making remediation decisions.
What we chose
Business unit as the default primary axis. Asset type becomes a filter, not the organizing principle. The whole IA was redesigned around organizational structure rather than scanner architecture. BU leads immediately understood their scope. Asset-type views are available but secondary.
Decision 03
Should target-setting live in a configuration area, or in the main dashboard workflow?
The tension
Settings-area placement keeps the main dashboard clean. But burying targets in settings signals that goals are an afterthought — which is exactly the problem we were trying to solve.
What we chose
First-class, inline target-setting. Targets appear alongside the live metrics they track. Creating a target takes three steps from the dashboard view. Progress is immediately visible. This placement transformed the feature from a configuration step into a daily workflow.

09 — Reflection

What this project taught me.

Taxonomy first
Before a single pixel was drawn, the team had to agree on what “critical” means across vulnerability domains. This was a weeks-long conversation between design, security engineering, and product leadership. Getting the taxonomy right made every subsequent design decision faster and more defensible.
Access shapes architecture
Committing to org-hierarchy-driven role access required rethinking the entire information architecture. BU became the organizing unit not just for display, but for permissions, ownership, and reporting. This had to be decided early. A late role-access decision would have required a near-total redesign.
Goals unlock adoption
CISOs stopped being passive dashboard consumers the moment they could set goals in it. Target-setting transformed the product from a monitoring view into a strategic accountability instrument — and drove leadership adoption far faster than the unified posture view alone.
Progressive disclosure
Designing for two audiences — a CISO skimming for 5 minutes and a vulnerability manager investigating for 5 hours — in one interface required very careful hierarchy. The answer was progressive disclosure at every level: posture at the top, BU breakdown on demand, asset-level detail on drill-down.
