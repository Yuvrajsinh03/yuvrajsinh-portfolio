The Brief

No system existed.
Engineers were the design system.

When I joined ComplyStream as the founding product designer, there was no visual foundation — no components, no tokens, no shared language between design and engineering. Every new feature was built from scratch. UI decisions were being made at the point of code, not at the point of design.

Inconsistency was everywhere: buttons with different radii across screens, bespoke spacing values, colour hex codes scattered across Jira tickets. The engineering team was doing their best, but they were filling a design vacuum with implementation decisions. That vacuum was costing the product quality, speed, and coherence.

The mandate was clear: build a design system from the ground up — one the entire engineering team would actually use as the single source of truth for every UI decision.

Approach

Foundation first,
then components.

Building a design system in isolation leads to a beautiful artefact nobody uses. The approach here prioritised the foundation layer — tokens, semantics, and decisions — before components, so that every component built on a shared, documented language engineers could map directly to code.

01
Audit & Inventory
Catalogued existing screens, extracted all unique colour values, type sizes, spacing, and component patterns in use across the product.

Defined the semantic token system — primitive values mapped to semantic aliases, covering colour, spacing, typography, radius, shadow, and motion.

Key Design Decisions

The choices that
shaped the system.

Decision 01
Shadcn as the base, not a full custom build
The thinking
A completely bespoke system takes months and requires significant maintenance overhead. Shadcn/UI gave us a production-ready, accessible component foundation with a headless architecture — meaning we own the code, not a package dependency. The system is fully themed to match ComplyStream's visual identity, so it reads as ours, not as a library.
Why it matters for engineering adoption
Engineers were already familiar with Shadcn's patterns and could map components directly to code without a learning curve. This decision reduced onboarding time to near-zero. By the time I finished the library, the first engineer was already using it on a live feature.
Decision 02
Semantic tokens over primitive tokens in component specs
The thinking
It would have been faster to reference hex codes directly in components. Instead, every component references a semantic token — color.surface.primary instead of #0F0F14. This adds a small upfront overhead but means the entire system can be re-themed from a single token file.
The downstream payoff
When ComplyStream's visual direction evolved, we changed 12 token values and propagated the update across all 35 components without touching a single component. That refactor would have taken days without the semantic layer. It took 20 minutes with it.
Decision 03
Document states and edge cases, not just the happy path
The thinking
Most design system components show the default state. But engineers build for all states — empty, loading, error, disabled, hover, focus, active. Each component in this system ships with all interactive states documented alongside accessibility notes and prop tables the engineering team can reference directly.
What changed in handoffs
The question "what does this look like when there's no data?" stopped appearing in Slack threads. Ambiguity in handoff dropped to near zero because the system answered the questions before engineers thought to ask them. That's the shift from a style guide to a real design system.

What This Unlocked

A system that grows
with the product.

01
Faster feature delivery, fewer design reviews
Engineers can begin building from day one of a feature without waiting for design to specify every UI detail. The system answers the questions before they're asked — component states, edge cases, accessibility behaviour are all documented. Design reviews shifted from "what does this look like?" to "is this the right pattern?"
02
Consistency at scale without a larger design team
As a solo designer, I can't review every pull request. The system acts as a second designer — every component in production references the same tokens, so the product looks coherent even when built independently by multiple engineers across multiple features simultaneously.
03
The foundation for every future product decision
Adding a new component now takes a fraction of the time it would have taken before — the token system, the component architecture, and the documentation pattern are all established. The system is built to evolve. It doesn't constrain future product decisions; it accelerates them.

Reflection

What I'd do
differently.

Involve engineers earlier
I built the token system before getting engineering input on naming conventions. We ended up renaming several tokens post-handoff to align with how engineers were referencing them in code. A one-hour naming session with the engineering lead before finalising the token architecture would have saved two days of renaming work.
Prioritise by frequency, not completeness
My instinct was to complete all 35 components before shipping the system. In retrospect, shipping the 10 most-used components on week three would have unlocked adoption 3–4 weeks earlier and given me real-world feedback before the remaining components were built. Perfect coverage is less valuable than early traction.
The unexpected lesson
A design system is a product, not a deliverable. The launch is the beginning, not the end. The most valuable thing I built wasn't the component library — it was the process of working with engineers to use it, which surfaced what actually needed to be in the system versus what I assumed would be needed.
